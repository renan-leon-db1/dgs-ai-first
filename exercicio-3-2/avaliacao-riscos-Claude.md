# Avaliação de Risco — Claude (co-reviewer)

> Avaliação feita de forma independente, sem acesso prévio à lista do Tech Lead (Parte 1). Baseada no resumo dos 4 artefatos do enunciado + evidências lidas diretamente no repositório `novatech-assistant` durante a sessão.

| Artefato | Risco de ter sido gerado/alterado por IA | O que verificar antes do go-live |
|---|---|---|
| **AGENTS.md** — gerado pelo Claude, refinado 4x, 15 páginas (465 linhas reais) | Um documento prescritivo de 465 linhas, escrito em 4 rodadas, tem alta chance de conter regras que se sobrepõem ou contradizem entre si — cada refinamento tende a adicionar sem revisar o que já existia. Além disso, é um documento que nenhum humano necessariamente leu por completo antes de virar fonte de verdade para o Copilot; a regra "em caso de conflito, este arquivo prevalece" (linha 5) significa que qualquer contradição interna vira ambiguidade estrutural para todo agente que o consome, não um bug isolado. Risco concreto já encontrado no código: a skill `azure-functions-endpoint.md` proíbe explicitamente criar `validator.ts` separado ("toda validação vive em `schema.ts`"), mas o endpoint de query real tem exatamente um `src/functions/query/validator.ts` — ou seja, o próprio código do projeto já viola uma regra do conjunto AGENTS.md/skills, sinal de que a regra não foi (ou não pôde ser) enforçada na prática. | 1) Fazer uma leitura linha a linha procurando contradições entre seções (ex.: regra de logging vs. regra de erros, escritas em momentos diferentes). 2) Rodar uma amostra do código já gerado contra as regras DEVE/NÃO DEVE do documento — não confiar que "documento existe" implica "documento é seguido" (achado real: `validator.ts` viola a própria skill). 3) Confirmar que as 4 rodadas de refinamento não deixaram nenhuma regra "morta" (referenciando uma decisão de ADR que já foi substituída). |
| **Skills** (Foundation refinada após testes; Domain e Artifact nunca refinadas) | O risco não é "skills geradas por IA podem ter erro" em abstrato — é que já sabemos que a primeira versão da Foundation tinha problema suficiente para justificar refinamento. Domain e Artifact nunca passaram pelo mesmo teste de fogo. Como as skills de Domain dependem explicitamente das de Foundation (a própria `azure-functions-endpoint.md` lista "Foundation skills que devem ser lidas antes" e diz que sem elas "o Copilot tende a gerar `any` implícito, `try/catch` genérico com `console.log`"), qualquer falha equivalente nas não-refinadas provavelmente já está silenciosamente presente em código gerado a partir delas, só que ninguém testou para descobrir. | 1) Rodar o mesmo processo de validação que revelou os problemas na Foundation, mas em Domain e Artifact — não assumir que "não encontramos problema" significa "não tem problema", pode significar "não testamos igual". 2) Auditar pelo menos um artefato gerado a partir de cada skill não refinada contra os exemplos DO/DON'T dela (ex.: pegar um endpoint real gerado com `azure-functions-endpoint.md` e ver se ele realmente segue a estrutura `index.ts`/`handler.ts`/`schema.ts` exigida, não uma variação livre). 3) Priorizar Domain sobre Artifact — Domain afeta código de produção (endpoints, integração Azure), Artifact afeta scaffolding de testes/UI, risco menor se falhar. |
| **Pipeline de ingestão + query endpoint** (~60-70% gerado por Copilot) | O risco central não é "IA escreveu a maior parte do código" — é que não existe spec formal contra a qual isso foi validado: `specs/pipeline-ingestao/requirements.md`, `plan.md` e `specs/query-endpoint/plan.md` estão vazios no repositório. Isso significa que os 60-70% gerados pelo Copilot foram aceitos com base em "parece certo" / testes que passam, não em um contrato de requisitos revisado. Some a isso o fato já descoberto de que 12% das respostas em produção estão incorretas (alucinação, doc desatualizado, chunk errado); nada garante que esse erro está nos 30-40% escritos por humano ou nos 60-70% gerados por IA, sem isso mapeado o time pode estar corrigindo o lugar errado. | 1) Preencher retroativamente ao menos `requirements.md` do pipeline e do query endpoint com o que foi de fato implementado, e então gap-analisar contra o código real — isso frequentemente revela decisões implícitas que ninguém documentou. 2) Isolar, dos 12% de erro conhecidos, quais componentes de código eles atravessam (chunking? retrieval? prompt-building? formatação de resposta?) e cruzar com quais desses trechos vieram majoritariamente do Copilot. 3) Cobertura de 75% em testes de integração — perguntar quais 25% NÃO estão cobertos, porque é exatamente aí que erros gerados por IA e nunca revisados tendem a se esconder. |
| **System prompt** — iterado 6x sem documentar por quê | `prompts/prompt-changelog.md` existe como arquivo, mas está vazio — a intenção de documentar existia, a prática não aconteceu. Isso não é só "falta de contexto histórico": é ausência de capacidade de rollback informado. Se a v6 (atual) causar um comportamento ruim identificado em produção, ninguém sabe se deve reverter para v5, v4 ou reescrever do zero, porque não há registro do que mudou entre elas nem por quê. Em um sistema onde o system prompt é a única linha de defesa probabilística contra alucinação, isso é crítico, não cosmético. | 1) Reconstruir o changelog retroativamente via `git log` do arquivo `prompts/system-prompt.md` (ou histórico equivalente), mesmo que de forma aproximada — melhor um changelog reconstituído tardiamente do que nenhum. 2) Testar a v6 atual isoladamente contra os 12% de casos de erro conhecidos, para saber se a versão atual é a causa ou não. 3) Congelar o processo a partir de agora: nenhuma nova iteração do prompt entra sem uma linha no changelog (motivo + o que mudou) — isso é barato de implementar e evita que o mesmo problema se repita pós-go-live. |
